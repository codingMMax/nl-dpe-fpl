Pproj

searched{1, 2, 4}

What it isCopies of the three projection GEMMs (WQ, WK, WV). Token t goes to copy t mod Pproj, so Pproj tokens are projected at the same time and the X stream is Pproj times wider.

In hardware3·Pproj gemm_top instances of V crossbars each. Each copy is one input channel of the DIMMs it feeds: the QK DIMM gets Pproj A channels and Pproj B channels, the PV DIMM Pproj B channels, each with its own LOG converter crossbar. att_ctrl keeps one admission counter per copy. The X port is Pproj·V·40 bits wide.

Cost and effect+3·V GEMM crossbars and +3 converters per copy. Cycles: 2 copies ×0.59–0.92, 4 copies ×0.39–0.91 of 1 copy (model). It pays most where the projections set the pace: large dm, small R.

GuardsRow frame: A_CH = Pproj ≤ NB = I/Bkv. Write rate per slice port ≤ 1 word/cycle (worst 0.76, the Q port at Pproj 4).

NE

searched{d, 2d}

What it isThe QK DIMM's farm: EXP crossbars computing Q·K⊤ in the log domain. Crossbar f works on feature column k = f / NG of output group f mod NG, so the farm finishes NG = NE/d score windows per wave.

In hardwareThe farm is cut into ns = NE/16 slices of XS = 16 crossbars; each slice has its own A and B memories, its own copy of the window engine and its part of the adder trees. NG is also the number of output channels (E4), so it sets how many input FIFOs the online softmax builds (S_CH).

Cost and effectNE crossbars (EXP, I×I). Halving the farm doubles the waves TW = WK/NG. NE = d instead of 2d: cycles ×1.005–1.17, d fewer crossbars (model).

GuardsK = d ≤ NE; NG ≤ WK (whole windows per wave); NG ≤ XS.

Fixed, each with its reason

One value per build; the DSE does not search them.

NEP

fixed · open2d

What it isThe PV DIMM's farm: EXP crossbars computing P·V. NGPV = NEP/Bkv output groups, which are the accumulator's input channels P_CH (E8).

In hardwareSame slice structure as the QK DIMM, with ns = NEP/16 slices of Ks = 16/NG keys. Each output group feeds one o_part FIFO in the accumulator.

Why fixedNEP = d fails the RTL guards on every build as specified: the accumulator needs NOC ≤ P_CH = NEP/16, because each crossbar of a wave reads its window from its own FIFO, and the floor rule asks NOC = 6 at d 64 while P_CH = 4. With NOC capped at P_CH it fits on the 288 builds with I ≥ 128 (at I = 64 the PV log P staging overruns): cycles ×1.02–1.21, crossbars −68 / −36 / −18 (×0.68–0.81). Your decision (LEDGER Needs you 2).

NEXP

fixed · rule2

What it isEXP crossbars in the online softmax. Each reads one window of scores, subtracts the row max, clamps to −128 and turns it into P; the words it pops are the log P stream (E5).

In hardwareNEXP feed units, each with a 4-deep FIFO and one crossbar (extent I×I); the score store gets max(2, NEXP) banks. E5 has NEXP lanes, so the PV DIMM's A port has NEXP channels, each with its own window stager pair.

Why fixedThe rule: the smallest power of two whose EXP stage keeps up with the score stream. It gives 2 on all 72 rows. More crossbars gave at most 12 % fewer cycles for twice the crossbars (earlier model).

NOC

fixed · floor rule6–8 at d 64 · 4 · 2

What it isCrossbars per accumulator group. There are two groups, LOG and EXP, so 2·NOC crossbars. A run's S×d result is Poc = S·d/I windows; window p runs on crossbar p mod NOC in wave p / NOC.

In hardwarePer crossbar index: one LOG crossbar, one EXP crossbar and three memories (lo, e, so). Both groups run lock-step from their crossbar 0. W = ⌈Poc/NOC⌉ waves per block.

RuleThe smallest NOC whose pass time T(⌈Poc/NOC⌉) reaches the stream floor max(⌈S·Bkv/5⌉, T(1)). BERT-Tiny at 128×128: Poc = 64, NOC = 6, W = 11.

Guards1 ≤ NOC ≤ Poc; NOC ≤ P_CH (this is what blocks NEP = d).

Bkv

fixed16

What it isKeys per block, the step of the online softmax. A tile is S query rows × Bkv keys; B = n/Bkv blocks per run.

In hardwareThe QK DIMM's output width N = Bkv; the PV DIMM's reduction length K = Bkv, so its trees have log2Bkv levels and o_part is 9 + log2Bkv = 13 bits. The K and V slots hold B matrices. The QK B staging credits per Bkv-row matrix.

Why 16The only value legal on every candidate: Bkv ≤ d excludes 32 and 64 at d = 16; NG ≤ WK excludes 8 at one point. Earlier model: ×0.99–1.07 cycles over {8, 32, 64}.

XS

fixed16 crossbars per slice

What it isThe slice size of both DIMMs. A slice is a self-contained piece of the farm: Ks = XS/NG columns of all NG groups.

In hardwarePer slice: its operand memories, one A and one B write port, its own window-engine copy led by its crossbar 0, and the first log2Ks tree levels. All slices start a job in the same cycle and stay in lock-step without signals between them.

Why fixedYour decision (2026-10-14). It bounds the fan-out of every control bit (at most 2,688 sinks instead of 16,384 for a one-engine 128-crossbar farm) and splits the operand write traffic. It changes cycles only through the start latency at I = 256.

Bq = S

fixedS = min(n, I)

What it isQuery rows per run: one run takes S rows of Q against all n keys, and Rb = n/S runs cover the head. S is as large as one crossbar window allows.

In hardwareS is the M of both DIMM jobs, the row count of the softmax and of the accumulator, and the size of their per-row tables (m, log α, log l). S < I is outside the space (not implemented; each run would re-stream K and V).

Credit sizes

fixedE1–E8 CAP

What they areEvery module-to-module edge is push + credit: the consumer's buffer holds CAP units, and the producer starts a unit only with a credit in hand. A crossbar's drain cannot stall, so this is the only flow control. A credit limits throughput when its loop is longer than CAP unit periods; E3 did (fixed 2026-10-15), the others were never checked.
